# Feature Specification: FW更新機能

**Feature Branch**: `002-fw-update`  
**Created**: 2026-02-27  
**Status**: Draft  
**Input**: User description: "機能追加：FW更新機能 - ボタン4を押すとFW更新待ちに入る。UARTでパソコンからFWを受け取る。FW更新待ち状態ではLED1,2,3は消灯しLED4を高速点滅。ボタン4でキャンセル可能。ボタン1,2,3の操作を受け付けない。30秒タイムアウト。データ破損検証。NCS標準機能を活用。"

## Clarifications

### Session 2026-02-27

- Q: FW更新の通信プロトコルは何を使用するか？ → A: MCUmgr（SMP over UART）
- Q: FW更新失敗時のユーザー通知方法は？ → A: LED点滅パターンで成功/失敗を通知
- Q: キャンセル後の通常動作復帰時のLED1〜3の状態は？ → A: 全LED消灯で復帰（状態を保持しない）
- Q: FW更新データ転送中にボタン4を押した場合の動作は？ → A: 転送中はキャンセル不可（転送完了まで待機）
- Q: FW更新成功後のMCUboot confirmの扱いは？ → A: 起動直後に自動confirm（ロールバックしない）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - FW更新の開始と完了 (Priority: P1)

ユーザーはデバイスのボタン4を押してFW更新待ち状態に入り、パソコンからUART経由で新しいファームウェアを送信し、デバイスのファームウェアを更新する。更新中はLED4が高速点滅し、更新待ち状態であることが視覚的に確認できる。ファームウェア受信後、データの整合性が自動的に検証され、正常であれば更新が適用される。

**Why this priority**: FW更新機能の中核フロー。この機能なしではFW更新自体が実現できない。

**Independent Test**: ボタン4の押下でFW更新モードに入り、パソコンからファームウェアを送信して更新が完了するまでの一連のフローをテストできる。

**Acceptance Scenarios**:

1. **Given** デバイスが通常動作中である, **When** ユーザーがボタン4を押す, **Then** デバイスがFW更新待ち状態に遷移し、LED1・LED2・LED3が消灯し、LED4が高速点滅を開始する
2. **Given** デバイスがFW更新待ち状態である, **When** パソコンからUART経由でファームウェアデータが送信される, **Then** デバイスがファームウェアデータを正常に受信する
3. **Given** ファームウェアデータの受信が完了した, **When** デバイスがデータの整合性を検証する, **Then** データに破損がなければLED4が3秒間点灯（成功通知）した後、ファームウェア更新が適用されデバイスが新しいファームウェアで再起動する
4. **Given** ファームウェアデータの受信が完了した, **When** デバイスがデータの整合性を検証する, **Then** データに破損が検出された場合、LED4が5回速い点滅（失敗通知）した後、更新を中止し現在のファームウェアを保持して通常動作に復帰する

---

### User Story 2 - FW更新のキャンセル（手動） (Priority: P2)

ユーザーはFW更新待ち状態でボタン4を再度押すことで、FW更新をキャンセルし通常動作に復帰する。誤ってFW更新モードに入った場合でも安全にキャンセルできる。

**Why this priority**: ユーザーが誤操作した場合の安全な復帰手段。操作ミスへの対応として重要。

**Independent Test**: FW更新待ち状態からボタン4でキャンセルし、通常動作に復帰することをテストできる。

**Acceptance Scenarios**:

1. **Given** デバイスがFW更新待ち状態でLED4が高速点滅中である, **When** ユーザーがボタン4を押す, **Then** FW更新待ち状態がキャンセルされ、LED4の高速点滅が停止し、全LEDが消灯して通常動作に復帰する
2. **Given** デバイスがFW更新待ち状態である, **When** ユーザーがボタン1・ボタン2・ボタン3を押す, **Then** それらの操作は無視され、FW更新待ち状態が維持される

---

### User Story 3 - FW更新のタイムアウト（自動キャンセル） (Priority: P3)

FW更新待ち状態に入ってから30秒以内にFW更新の通信が開始されない場合、自動的にFW更新待ち状態がキャンセルされ、全LEDが消灯する。デバイスが無期限にFW更新待ち状態に留まることを防止する。

**Why this priority**: デバイスがFW更新待ち状態で放置されるリスクを回避する安全機構。

**Independent Test**: FW更新待ち状態に入った後、30秒間通信を行わず、タイムアウトによる自動キャンセルを確認できる。

**Acceptance Scenarios**:

1. **Given** デバイスがFW更新待ち状態に遷移した, **When** 30秒以内にFW更新の通信が開始されない, **Then** FW更新待ち状態が自動的にキャンセルされ、全LEDが消灯して通常動作に復帰する
2. **Given** デバイスがFW更新待ち状態に遷移した, **When** 30秒以内にFW更新の通信が開始された, **Then** タイムアウトタイマーが停止され、FW更新が継続される

---

### User Story 4 - FW更新中のボタン操作制限 (Priority: P4)

FW更新待ち状態では、ボタン1・ボタン2・ボタン3による通常の操作（LED切り替えなど）を受け付けない。これにより、FW更新中に意図しない動作が発生することを防止する。

**Why this priority**: FW更新中の安全性を確保するための補助機能。

**Independent Test**: FW更新待ち状態でボタン1〜3を操作し、通常の動作が発生しないことを確認できる。

**Acceptance Scenarios**:

1. **Given** デバイスがFW更新待ち状態である, **When** ユーザーがボタン1を押す, **Then** LED1の状態は変化せず、操作は無視される
2. **Given** デバイスがFW更新待ち状態である, **When** ユーザーがボタン2を押す, **Then** LED2の状態は変化せず、操作は無視される
3. **Given** デバイスがFW更新待ち状態である, **When** ユーザーがボタン3を押す, **Then** LED3の状態は変化せず、操作は無視される

---

### Edge Cases

- FW更新中（データ転送中）にUART接続が切断された場合、デバイスは更新を中止し、LED4を5回速く点滅（失敗通知）した後、現在のファームウェアを保持して通常動作に復帰する
- FW更新待ち状態でボタン4を素早く連打した場合、チャタリング等による意図しない状態遷移が発生しない
- 受信したファームウェアサイズがデバイスの記憶領域を超える場合、適切にエラーを通知し更新を中止する
- FW更新中（データ転送中）にボタン4を押した場合、操作は無視され転送が継続する（転送中のキャンセルは不可）
- 電源が不安定な状態でFW更新が行われた場合でも、現在のファームウェアが破損しない（ブートローダーによる保護）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: デバイスは、通常動作中にボタン4が押されたとき、FW更新待ち状態に遷移しなければならない（MUST）
- **FR-002**: FW更新待ち状態では、LED1・LED2・LED3を消灯し、LED4を高速点滅（100ms間隔）させなければならない（MUST）
- **FR-003**: FW更新待ち状態では、MCUmgr（SMP over UART）プロトコルを使用してパソコンからファームウェアデータを受信できなければならない（MUST）
- **FR-004**: FW更新待ち状態でボタン4が押されたとき、FW更新待ちをキャンセルし通常動作に復帰しなければならない（MUST）
- **FR-005**: IDLE状態以外のすべての状態（FW更新待ち、転送中、検証中、通知中）では、ボタン1・ボタン2・ボタン3の操作を無視しなければならない（MUST）
- **FR-006**: FW更新待ち状態に入ってから30秒以内にFW更新の通信が開始されない場合、自動的にキャンセルし全LEDを消灯して通常動作に復帰しなければならない（MUST）
- **FR-007**: ファームウェアデータの受信完了後、データの整合性（破損の有無）を検証しなければならない（MUST）
- **FR-008**: データ整合性検証に成功した場合、新しいファームウェアを適用しデバイスを再起動しなければならない（MUST）
- **FR-009**: データ整合性検証に失敗した場合、更新を中止し現在のファームウェアを保持しなければならない（MUST）
- **FR-010**: FW更新中にUART接続が切断された場合、更新を中止し現在のファームウェアを保持して通常動作に復帰しなければならない（MUST）
- **FR-011**: FW更新処理は、NCS（nRF Connect SDK）が提供するMCUmgr + MCUbootベースの標準DFUメカニズムを活用しなければならない（MUST）
- **FR-012**: FW更新の整合性検証に成功した場合、LED4を3秒間点灯させて成功を通知しなければならない（MUST）
- **FR-013**: FW更新が失敗した場合（整合性検証失敗、UART切断等）、LED4を5回速く点滅（100ms間隔）させて失敗を通知した後、通常動作に復帰しなければならない（MUST）
- **FR-014**: 新しいファームウェアで起動後、アプリケーションは即座にMCUbootのconfirmを実行し、イメージを永続的に確定しなければならない（MUST）

### Non-Functional Requirements

- **NFR-001**: アプリケーションのFlash使用量は、nRF52840の1MBの80%（819KB）を超えてはならない（MUST）。MCUboot + MCUmgrの追加オーバーヘッドを含む
- **NFR-002**: アプリケーションのRAM使用量は、nRF52840の256KBの80%（204KB）を超えてはならない（MUST）
- **NFR-003**: メインスレッドのスタックサイズ（`CONFIG_MAIN_STACK_SIZE`）およびシステムワークキューのスタックサイズ（`CONFIG_SYSTEM_WORKQUEUE_STACK_SIZE`）は、使用量の根拠とともにresearch.mdに文書化しなければならない（MUST）
- **NFR-004**: ビルド後に `west build -t rom_report` / `west build -t ram_report` でメモリ使用量を実測し、NFR-001/NFR-002の閾値内であることを検証しなければならない（MUST）

### Key Entities

- **ファームウェアイメージ**: パソコンからUART経由で送信される更新用ファームウェアのバイナリデータ。サイズ、バージョン情報、整合性チェック用情報を含む
- **デバイス状態**: デバイスの動作モードを表す。「通常動作」と「FW更新待ち」の2つの状態を持つ。状態に応じてLED表示とボタン操作の受付が変化する
- **整合性チェック結果**: 受信したファームウェアデータの破損検証結果。合格の場合のみ更新が適用される

## Assumptions

- FW更新成功後、デバイスは新しいファームウェアで自動的に再起動する
- 新しいファームウェアで起動後、アプリケーションが即座にMCUbootのconfirmを実行し、イメージを永続的に確定する（自動ロールバックは行わない）
- LED4の高速点滅間隔は100ms（点灯100ms/消灯100msの200ms周期）を想定する
- FW更新データ転送中（通信開始後）にボタン4を押しても、データ転送は中断されない（転送完了まで待機する）
- FW更新待ちからキャンセルして通常動作に復帰した場合、キャンセル前のLED1〜3の状態は保持されず、全LED消灯状態で復帰する
- UART通信にはMCUmgr（SMP over UART）プロトコルを使用し、PC側は`mcumgr` CLIツールで操作する
- UART通信のボーレートや通信パラメータはNCS標準のMCUmgr設定に従う

## NCS標準機能との整合性に関する注記

以下の点について、NCS標準のFW更新機能（MCUboot + MCUmgr）との整合性を検討した結果を記載する：

1. **通信プロトコル**: MCUmgr（SMP over UART）をFW転送プロトコルとして使用する。NCS標準のDFUスタックそのものであり、PC側は`mcumgr` CLIツールを利用可能。
2. **ボタン4によるFW更新モード切替**: NCS標準のDFU（Device Firmware Update）は通常、常時受信可能な状態で動作するか、特定の条件で起動する。ボタン操作によるモード切替はアプリケーション層の実装で対応可能であり、NCS標準と矛盾しない。
3. **LED表示**: アプリケーション層の実装であり、NCS標準に影響なし。
4. **30秒タイムアウト**: アプリケーション層の実装であり、NCS標準に影響なし。
5. **データ整合性検証**: NCS標準のブートローダー（MCUboot）にはイメージ署名検証機能が組み込まれており、この要件は標準機能で対応可能。
6. **イメージ確定（confirm）**: 新FW起動直後に自動confirmを行う。MCUbootのtest/confirm方式を利用するが、自動ロールバックは行わない。
7. **ロールバック機能**: 起動直後に自動confirmするため、事実上ロールバックは発生しない。将来的に自己診断後のconfirm方式への変更も可能。

**結論**: ユーザー要件はNCS標準のFW更新機能と十分に整合しており、大きな仕様変更は不要と判断する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーがボタン4を押してから1秒以内にFW更新待ち状態への遷移が完了し、LED4の高速点滅が開始される
- **SC-002**: 有効なファームウェアイメージの転送・検証・適用・再起動が3分以内に完了する
- **SC-003**: FW更新操作の成功率が、正常なファームウェアイメージを使用した場合に100%である
- **SC-004**: 破損したファームウェアイメージが送信された場合、100%の確率で検出・拒否され、現在のファームウェアが保持される
- **SC-005**: タイムアウト（30秒）後、1秒以内にFW更新待ち状態が解除され通常動作に復帰する
- **SC-006**: FW更新プロセス中（更新待ち状態・データ転送中・検証中）にデバイスの現行ファームウェアが破損する確率が0%である
