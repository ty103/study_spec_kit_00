## 1. はじめに — なぜテストが必要なのか？

組み込みソフトウェアの開発では、コードを書いた後に「本当に正しく動くか？」を確認する必要があります。

確認方法として最も直感的なのは、**実機（マイコンボード）にプログラムを書き込んで、ボタンを押してみる** ことです。しかし、この方法には大きな問題があります。

| 問題 | 具体例 |
|------|--------|
| **時間がかかる** | コンパイル → 書き込み → 手動操作 → 目視確認で数分〜数十分 |
| **人間がミスする** | 「ボタン 3 を押したつもりがボタン 2 だった」 |
| **再現が難しい** | 「さっきは動いたのに、今度は動かない」 |
| **網羅できない** | 全ボタンの全組み合わせを毎回手動で試すのは非現実的 |
| **コード修正のたびに繰り返す** | 1 行修正しただけでも、全機能を再確認しないと安心できない |

これらの問題を解決するのが **自動テスト** です。テストをプログラムとして書いておけば、**コマンド一発で何十ものテストを数秒で実行** でき、結果も自動的に合格/不合格で判定されます。

## 2. ユニットテストとは何か？

**ユニットテスト（単体テスト）** とは、プログラムの一部分（関数やモジュール）を **個別に取り出して** 正しく動作するか確認するテストです。

### たとえ話

料理に例えると：

- **ユニットテスト** = 各食材の味見（「この塩の分量は適切か？」「卵は新鮮か？」）
- **統合テスト** = 複数の食材を組み合わせた味見（「煮込んだスープの味は？」）
- **手動テスト** = 完成した料理をお客さんに出して反応を見る

ユニットテストは、**問題を小さな単位で早期に発見する** ためのものです。

### C 言語でのユニットテストのイメージ

テスト対象の関数が以下のようなものだとします：

```c
// 2つの数を足す関数
int add(int a, int b) {
    return a + b;
}
```

ユニットテストでは、この関数に対して以下のような確認を行います：

```c
// テスト: 1 + 2 は 3 になるはず
assert(add(1, 2) == 3);

// テスト: 0 を足しても変わらないはず
assert(add(5, 0) == 5);

// テスト: 負の数も計算できるはず
assert(add(-1, -2) == -3);
```

このように、**「入力を与えて、期待通りの出力が返ってくるか？」** を機械的にチェックするのがユニットテストです。

## 3. ztest とは何か？

### 一言で言うと

**ztest** は、Zephyr RTOS が提供する **C 言語用のテストフレームワーク** です。

### テストフレームワークとは？

テストフレームワークとは、テストを書くための「お膳立て」をしてくれる仕組みです。自分でゼロからテストの仕組みを作らなくても、**決まったルールに従ってテストコードを書けば、自動で実行・判定してくれる** ようになります。

他の言語にも同様のフレームワークがあります：

| 言語 | テストフレームワーク |
|------|---------------------|
| C (Zephyr) | **ztest** |
| C (一般) | Unity, CMocka |
| Java | JUnit |
| Python | pytest |
| JavaScript | Jest |

### ztest が提供するもの

ztest は以下の仕組みを提供しています：

#### (1) テストケースを書くためのマクロ

```c
ZTEST(スイート名, テスト名)
{
    // ここにテストの内容を書く
}
```

- **テストケース**: 1 つの確認項目（例：「ボタン 1 を押したら LED 1 が点灯するか？」）
- **テストスイート**: 関連するテストケースをまとめたグループ（例：「LED トグル機能のテスト一式」）

`ZTEST` は C 言語のマクロです。見た目は関数のようですが、内部でテストの登録処理を自動生成してくれます。

#### (2) 結果を判定するためのアサーション関数

「アサーション」とは、**「この条件は成り立つはずだ」と宣言すること** です。条件が成り立たなければ、テスト失敗として報告されます。

```c
// 値が等しいことを確認する
zassert_equal(実際の値, 期待する値, "失敗時のメッセージ");

// 条件が true であることを確認する
zassert_true(条件式, "失敗時のメッセージ");

// 条件が false であることを確認する
zassert_false(条件式, "失敗時のメッセージ");

// 2つの値が等しくないことを確認する
zassert_not_equal(実際の値, 比較する値, "失敗時のメッセージ");
```

#### (3) テストの実行順序を管理する仕組み

```c
ZTEST_SUITE(スイート名, 条件, セットアップ, 各テスト前の処理, 各テスト後の処理, 後片付け);
```

- **各テスト前の処理（before_each）**: 各テストケースが実行される前に毎回呼ばれる関数。テストの初期状態をリセットするために使う。
- **各テスト後の処理（after_each）**: 各テストケースが終了した後に毎回呼ばれる関数。
- `NULL` を指定すると「何もしない」という意味になる。

## 4. Twister とは何か？

### 一言で言うと

**Twister** は、Zephyr RTOS が提供する **テスト実行ツール（テストランナー）** です。

### テストランナーとは？

テストランナーとは、テストのビルド（コンパイル）から実行、結果の集計までを **自動的に行ってくれるツール** です。

### Twister が行う処理の流れ

Twister を実行すると、内部では以下の処理が自動的に行われます：

```
   ┌─────────────────────────────────────────────────┐
   │  1. テストプロジェクトの検出                      │
   │     testcase.yaml を探して、テスト対象を特定する   │
   └──────────────────────┬──────────────────────────┘
                          │
                          ▼
   ┌─────────────────────────────────────────────────┐
   │  2. ビルド（コンパイル）                          │
   │     テストコード + テスト対象コードを              │
   │     指定プラットフォーム向けにビルドする           │
   └──────────────────────┬──────────────────────────┘
                          │
                          ▼
   ┌─────────────────────────────────────────────────┐
   │  3. テスト実行                                    │
   │     ビルドした実行ファイルを起動し、               │
   │     各テストケースを順番に実行する                 │
   └──────────────────────┬──────────────────────────┘
                          │
                          ▼
   ┌─────────────────────────────────────────────────┐
   │  4. 結果の判定・レポート生成                      │
   │     合格/不合格を判定し、レポートファイルを出力     │
   │     （XML, JSON, コンソール出力など）              │
   └─────────────────────────────────────────────────┘
```

### 開発者がやること vs Twister がやること

| 開発者がやること | Twister がやること |
|------------------|---------------------|
| テストコードを書く（ztest を使って） | テストコードをビルドする |
| `testcase.yaml` を書く（設定ファイル） | 実行ファイルを起動する |
| `west twister` コマンドを実行する | テスト結果を集計する |
| 結果を確認する | レポートを生成する |

## 5. ztest と Twister の関係

初めて触れると「ztest と Twister はどう違うの？」と混乱しがちです。以下の図で整理します。

```
  開発者が書くもの                    ツールが処理するもの
  ────────────────                    ──────────────────

  ┌──────────────┐
  │  テストコード  │ ─── ztest のマクロ・アサーション関数を使って書く
  │  (main.c)    │
  └──────┬───────┘
         │                     ┌──────────────────────────┐
         │                     │       Twister             │
         │  [ビルド対象として]→  │  1. ビルド               │
         │                     │  2. 実行                  │
         │                     │  3. 結果判定・レポート      │
         │                     └──────────────────────────┘
  ┌──────────────┐
  │ testcase.yaml │ ─── Twister への指示書（どのテストを、どのボードで実行するか）
  └──────────────┘
```

つまり：

- **ztest** = テストを **書く** ための道具（ライブラリ）
- **Twister** = テストを **実行する** ための道具（ツール）

Java で例えると、**ztest は JUnit、Twister は Maven の `mvn test` コマンド** に相当します。

## 6. native_sim — PC 上でテストを実行する仕組み

### なぜ PC 上で実行するのか？

通常、Zephyr アプリケーションは nRF52840 などのマイコンボード上で動きます。しかし、テストのたびにボードに書き込んで実行するのは以下の理由で非効率です：

- ボードへの書き込みに数十秒かかる
- ボードが手元にないと実行できない
- CI（自動テスト環境）ではボードが接続されていない

### native_sim とは？

**native_sim** は、Zephyr が提供する **仮想的なマイコンボード** です。

実際のマイコンの代わりに、**PC の CPU 上で Zephyr アプリケーションを直接実行** できます。GPIO（ピン入出力）やタイマーなどのハードウェア機能はシミュレーション（模倣）されます。

```
  通常の実行                    テスト時の実行
  ──────────                    ──────────────

  ┌──────────────┐             ┌──────────────┐
  │ アプリケーション │             │ テストコード   │
  │ (main.c)     │             │ (main.c)     │
  └──────┬───────┘             └──────┬───────┘
         │                            │
  ┌──────┴───────┐             ┌──────┴───────┐
  │  Zephyr RTOS  │             │  Zephyr RTOS  │
  └──────┬───────┘             └──────┴───────┘
         │                            │
  ┌──────┴───────┐             ┌──────┴───────┐
  │  nRF52840     │             │  native_sim   │
  │ (実際のボード)  │             │（PC 上の仮想ボード）│
  └──────────────┘             └──────────────┘
```

テスト対象のコード（`led_toggle.c` など）は **実際のボードでも native_sim でも同じコード** が動きます。これにより、PC 上で高速にテストを実行しつつ、実機と同じロジックを検証できます。

## 7. テストコードの書き方（実例で理解する）

本プロジェクトの実際のテストコードを使って、ztest の書き方を説明します。

### テスト対象: `led_toggle.c`

LED のトグル（点灯/消灯の切り替え）ロジックを実装した関数です：

```c
// ボタンが押されたら、対応する LED の ON/OFF を切り替える
uint32_t led_toggle_process(uint32_t button_state, uint32_t has_changed);

// 現在の LED 状態を取得する
uint32_t led_toggle_get_state(void);

// LED 状態を初期化する（すべて消灯にする）
void led_toggle_reset(void);
```

### テストコードの構成要素

#### (1) ヘッダのインクルード

```c
#include <zephyr/ztest.h>       // ztest フレームワーク本体
#include <dk_buttons_and_leds.h> // ボタン・LED の定数定義（スタブ版）
#include "led_toggle.h"          // テスト対象の関数宣言
```

#### (2) テスト前処理の定義

各テストケースが実行される **前に毎回呼ばれる関数** を定義します。テスト同士が互いに影響し合わないよう、LED の状態をリセットしています。

```c
static void before_each(void *f)
{
    ARG_UNUSED(f);       // 引数 f は今回使わないので、コンパイラ警告を抑制
    led_toggle_reset();  // LED 状態を全消灯にリセット
}
```

#### (3) テストスイートの登録

```c
ZTEST_SUITE(led_toggle_init,   NULL, NULL, before_each, NULL, NULL);
ZTEST_SUITE(led_toggle_single, NULL, NULL, before_each, NULL, NULL);
ZTEST_SUITE(led_toggle_multi,  NULL, NULL, before_each, NULL, NULL);
ZTEST_SUITE(led_toggle_edge,   NULL, NULL, before_each, NULL, NULL);
```

`ZTEST_SUITE` の引数は以下の通りです：

| 引数 | 意味 | この例での値 |
|------|------|-------------|
| 第 1 引数 | スイート名（グループの名前） | `led_toggle_init` など |
| 第 2 引数 | スイートを実行する条件 | `NULL`（常に実行） |
| 第 3 引数 | スイート全体の初期化関数 | `NULL`（なし） |
| 第 4 引数 | 各テストの前に実行する関数 | `before_each` |
| 第 5 引数 | 各テストの後に実行する関数 | `NULL`（なし） |
| 第 6 引数 | スイート全体の後片付け関数 | `NULL`（なし） |

#### (4) テストケースの記述

```c
// テストスイート「led_toggle_init」に属するテスト「test_reset_sets_all_leds_off」
ZTEST(led_toggle_init, test_reset_sets_all_leds_off)
{
    // led_toggle_get_state() の戻り値が 0 であることを確認する
    // 0 = すべての LED が消灯している状態
    zassert_equal(led_toggle_get_state(), 0,
                  "After reset, LED state must be 0");
}
```

このテストが行っていることを日本語で言い換えると：

> 「リセット直後に LED の状態を取得したら、戻り値は 0（全消灯）であるはず。もし 0 でなかったらテスト失敗。」

#### (5) もう少し複雑なテストの例

```c
// ボタン 1 を押したら LED 1 が点灯するかテスト
ZTEST(led_toggle_single, test_button1_toggles_led1_on)
{
    // ボタン 1 の押下イベントを処理する
    // 引数: button_state = BTN1が押されている, has_changed = BTN1が変化した
    uint32_t state = led_toggle_process(DK_BTN1_MSK, DK_BTN1_MSK);

    // 戻り値が LED1 のビットマスクと一致するか？
    zassert_equal(state, DK_LED1_MSK,
                  "Button 1 press should turn LED 1 ON");

    // 内部状態も LED1 が ON になっているか？
    zassert_equal(led_toggle_get_state(), DK_LED1_MSK);

    // ボタン押下が検出されたことを示すフラグが立っているか？
    zassert_equal(led_toggle_had_press(), 1);
}
```

テスト 1 つの中で `zassert_equal` を複数回呼んでいます。**すべてのアサーションが成功して初めて、そのテストケースが「合格」** となります。1 つでも失敗すれば、そのテストケースは「不合格」です。

## 8. テストプロジェクトの構成

テストを実行するためには、テストコード以外にもいくつかの設定ファイルが必要です。本プロジェクトの構成は以下の通りです：

```
tests/unit/
├── CMakeLists.txt      ← ビルド設定（何をコンパイルするか）
├── prj.conf            ← Zephyr の設定（ztest を有効にする）
├── testcase.yaml       ← Twister への指示書
├── src/
│   ├── main.c          ← LED トグルのテストコード
│   └── fw_update_test.c ← FW アップデートのテストコード
└── stubs/
    └── dk_buttons_and_leds.h  ← ハードウェア定数のスタブ
```

### 各ファイルの役割

#### `testcase.yaml` — Twister への指示書

```yaml
tests:
  app.led_toggle_button.unit:    # テストの識別名
    tags:                        # 分類用のタグ
      - button
      - led
      - unit_test
      - fw_update
    platform_allow:              # 実行を許可するプラットフォーム
      - native_sim
    integration_platforms:       # CI で使用するプラットフォーム
      - native_sim
```

Twister はこのファイルを読んで、「このディレクトリにテストがある」「native_sim で実行する」ということを把握します。

#### `prj.conf` — Zephyr の設定ファイル

```
CONFIG_ZTEST=y    ← ztest フレームワークを有効にする
CONFIG_LOG=y      ← ログ出力を有効にする
```

Zephyr では、使いたい機能を `CONFIG_xxx=y` で明示的に有効にする必要があります。`CONFIG_ZTEST=y` を書かないと、ztest のマクロやアサーション関数が使えません。

#### `CMakeLists.txt` — ビルド設定

```cmake
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(led_toggle_button_test)

target_sources(app PRIVATE
  src/main.c                                         # テストコード
  src/fw_update_test.c                               # テストコード（FW更新）
  ${CMAKE_CURRENT_SOURCE_DIR}/../../src/led_toggle.c  # テスト対象の実装
  ${CMAKE_CURRENT_SOURCE_DIR}/../../src/fw_update.c   # テスト対象の実装
)

target_include_directories(app BEFORE PRIVATE
  ${CMAKE_CURRENT_SOURCE_DIR}/stubs   # スタブヘッダの場所（優先的に探す）
)
target_include_directories(app PRIVATE
  ${CMAKE_CURRENT_SOURCE_DIR}/../../src  # テスト対象のヘッダの場所
)
```

ポイントは、テストコード（`src/main.c`）と **テスト対象のコード（`../../src/led_toggle.c`）を一緒にビルドしている** ことです。テストコードからテスト対象の関数を直接呼び出すことで、関数の動作を検証します。

## 9. スタブ（stub）— ハードウェアの代わりを用意する

### スタブとは？

**スタブ** とは、テスト時に使う **本物の代わりとなる偽物のコード** です。

`led_toggle.c` は内部で `DK_BTN1_MSK` や `DK_LED1_MSK` といった定数を使っています。これらは本来、Nordic 社の nRF Connect SDK が提供する `dk_buttons_and_leds.h` で定義されています。しかし、このヘッダは実機の GPIO ドライバに依存しており、PC 上ではビルドできません。

そこで、テスト用に **同じ名前の定数だけを定義した簡易版ヘッダ** を用意します。これがスタブです。

### 本物 vs スタブ

```
本物（nRF Connect SDK 版）:
  dk_buttons_and_leds.h
  ├── DK_BTN1_MSK などの定数定義
  ├── GPIO ドライバの初期化関数
  ├── LED の物理制御関数
  └── ボタン割り込みの登録関数

スタブ（テスト用）:
  stubs/dk_buttons_and_leds.h
  ├── DK_BTN1_MSK などの定数定義  ← これだけ！
  └── （GPIO やドライバ関連は一切なし）
```

テスト対象の `led_toggle.c` は定数だけ使って **純粋なロジック演算** を行っているので、スタブで定数さえ提供すれば、PC 上でも問題なくビルド・実行できます。

`CMakeLists.txt` の `BEFORE PRIVATE` 指定により、nRF SDK 本体よりも先にスタブのヘッダが見つかるようになっています。

## 10. テストの実行方法

### コマンド

本プロジェクトでは、`scripts/test.sh` を使ってテストを実行します：

```bash
# Docker コンテナ内で全テストを実行（macOS の場合）
docker compose run --rm test

# Linux 環境で直接実行する場合
./scripts/test.sh

# 詳細な出力を見たい場合
./scripts/test.sh --verbose
```

内部では、以下の `west twister` コマンドが実行されています：

```bash
west twister \
    -T study_spec_kit_00/tests/unit \  # テストコードのディレクトリ
    -p native_sim \                     # PC 上で実行（native_sim）
    -O study_spec_kit_00/twister-out    # 結果の出力先
```

### 実行の内部動作

`west twister` が実行されると、以下の処理が行われます：

```
1. tests/unit/testcase.yaml を発見
       ↓
2. tests/unit/ のコードを native_sim 向けにビルド（cmake + ninja）
       ↓
3. 生成された実行ファイル（zephyr.exe）を PC 上で実行
       ↓
4. ztest が登録された全テストケースを順番に実行
       ↓
5. 各テストの合格/不合格を判定
       ↓
6. 結果をコンソールに表示し、レポートファイルを出力
```

## 11. テスト結果の見方

### コンソール出力（成功時）

```
Running TESTSUITE led_toggle_init
=============================================
START - test_reset_sets_all_leds_off
 PASS - test_reset_sets_all_leds_off in 0.001 seconds
START - test_reset_clears_press_flag
 PASS - test_reset_clears_press_flag in 0.001 seconds
...
=============================================
TESTSUITE led_toggle_init succeeded
---------------------------------------------
SUITE PASS - 100.00%
=============================================
```

- `PASS` = テスト合格（期待通りの動作）
- `FAIL` = テスト不合格（期待と異なる動作）

### コンソール出力（失敗時）

```
START - test_button1_toggles_led1_on
Assertion failed at tests/unit/src/main.c:80:
    Button 1 press should turn LED 1 ON: value 0x00 is not equal to 0x01
 FAIL - test_button1_toggles_led1_on in 0.001 seconds
```

失敗時は以下の情報が表示されます：

- **どのファイルの何行目** で失敗したか（`main.c:80`）
- **失敗時のメッセージ**（`Button 1 press should turn LED 1 ON`）
- **実際の値と期待値**（`0x00 is not equal to 0x01`）

### 出力ファイル

テスト結果は `twister-out/` ディレクトリにも保存されます：

| ファイル | 内容 |
|----------|------|
| `twister.json` | テスト結果の詳細（JSON 形式） |
| `twister.xml` | テスト結果（JUnit XML 形式、CI ツールで使用） |
| `handler.log` | テスト実行時の詳細ログ |

## 12. よくある疑問

### Q. テスト対象のコードを修正したら、テストも修正しないといけない？

関数のインターフェース（引数や戻り値）が変わった場合はテストも修正が必要です。内部のロジックだけ変えた場合は、テストはそのまま通るはずです。もしテストが失敗したら、修正が意図通りか確認してください。

### Q. テストコードにバグがあったらどうなる？

テストコード自体にバグがある場合、本来合格すべきテストが不合格になったり、逆に不合格にすべきものが合格になったりします。テストコードもレビュー対象であり、正しく書くことが重要です。

### Q. 全部の関数にテストを書くべき？

理想的にはすべての関数にテストを書くのが望ましいですが、現実的には **ロジックを含む関数**（条件分岐や計算がある関数）を優先します。単純な getter/setter やハードウェア制御だけの関数はテストの優先度が低いです。

### Q. native_sim で合格しても、実機で動かない可能性はある？

あります。native_sim はロジックの正しさを検証するものであり、タイミング（リアルタイム性）やハードウェア固有の挙動は検証できません。ロジックのテストは native_sim で、ハードウェアの統合テストは実機で行うのが一般的です。

### Q. テストはいつ実行するべき？

- コードを修正した後（デグレ検出）
- 新機能を追加した後（仕様通りか確認）
- プルリクエスト作成時（CI で自動実行）
- 定期的に（知らないうちに壊れていないか確認）

## 13. 用語集

| 用語 | 読み方 | 意味 |
|------|--------|------|
| ユニットテスト | — | 関数やモジュール単位で正しく動くかを確認するテスト |
| テストフレームワーク | — | テストの記述・実行・判定を支援するライブラリ |
| テストランナー | — | テストのビルド・実行・結果集計を自動で行うツール |
| テストケース | — | 1 つの確認項目（1 つの `ZTEST(...)` ブロック） |
| テストスイート | — | 関連するテストケースをまとめたグループ |
| アサーション | — | 「この条件は成り立つはず」と宣言すること |
| スタブ | — | テスト時に使う、本物の代わりとなる簡易的なコード |
| ztest | ゼットテスト | Zephyr RTOS のテストフレームワーク |
| Twister | ツイスター | Zephyr RTOS のテストランナー |
| native_sim | ネイティブシム | PC 上で Zephyr アプリを実行する仮想ボード |
| Zephyr RTOS | ゼファー | 組み込み向けリアルタイム OS |
| West | ウェスト | Zephyr のビルド・管理用メタツール |
| CI | シーアイ | 継続的インテグレーション。コード変更時に自動でテストを実行する仕組み |
| ビットマスク | — | 各ビットに意味を持たせた整数値。ボタンや LED の状態を表現するのに使う |
| デグレ | — | コード修正で以前動いていた機能が壊れること（デグレードの略） |
